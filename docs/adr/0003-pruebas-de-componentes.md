# Pruebas de componentes junto a las pruebas puras
Fecha: 2026-10-03

Para cubrir el cableado entre pantallas, estado y decisiones puras de Relay (#51), añadimos un arnés de componentes Android con Jest 29.7.0, jest-expo 57.0.5, @react-native/jest-preset 0.86.3, React Native Testing Library 13.3.3 y react-test-renderer 19.2.3, coincidente con React. Las herramientas y sus tipos son dependencias de desarrollo fijadas en package.json y package-lock.json. No se modifica el runtime de la app, del Puente ni del protocolo. Esta decisión no sustituye los ADR 0001 y 0002.

Las pruebas ejecutan componentes, hooks, efectos, manejadores y AppProvider reales. Un setup compartido controla únicamente almacenamiento nativo, biometría, cámara, ciclo de vida, apertura de enlaces, reloj, transporte y solicitudes de navegación. Las decisiones core permanecen reales; una petición de red no declarada falla el caso aunque la app capture el error. Las pruebas no acceden a dispositivos ni servicios reales.

El transformador de pruebas usa el babel-preset-expo instalado y activa React Compiler para código propio mediante supportsReactCompiler, sin compilar dependencias ni modificar Babel de producción. La resolución y los mocks corresponden a Android. El montaje omite el navegador completo cuando solo se comprueba la solicitud de navegación; las pruebas de rutas podrán usar el entorno específico de Expo Router.

Las suites puras y de plugins conservan node --test. Los componentes viven exclusivamente en mobile/tests/components con sufijo .component.test.tsx, fuera del árbol de rutas; sus tipos Jest se aíslan en un tsconfig propio. El gate incorpora test:components, con un máximo de cuatro procesos, sin watch ni cobertura y con caché bajo .expo. Se mide el costo frío y caliente y se conserva un tiempo de segundos. Los tests y sus dependencias no son importados por producción; se comprueba su ausencia del grafo exportado de Android.

Cada contrato crítico se comprueba mediante interacción y mutación temporal del cableado. Las pruebas estáticas se retiran solo al existir cobertura conductual equivalente, preservando mientras tanto los contratos aún no migrados. No se crean nuevas comprobaciones de texto de componentes.

Se descartan un renderer artesanal sobre Node por duplicar la infraestructura de Expo, un montaje web por omitir ramas nativas y un emulador obligatorio por costo. El renderer elegido está deprecado, pero coincide con el conjunto publicado para este SDK; su sustitución se evalúa al actualizar SDK/React. El arnés comprueba conducta JavaScript y props nativas, no sustituye la validación de biometría y presentación real en Android.

Para ejecutar el `import()` diferido de `openTailscale` bajo Jest 29 en CommonJS, añadimos `@babel/plugin-transform-dynamic-import` 7.29.7 como dependencia de desarrollo exacta. Se activa únicamente para código propio en el adaptador Babel de pruebas y convierte ese import en un require diferido; el preset de Expo ya proporciona la transformación CommonJS necesaria. No se añade a Babel ni Metro de producción: `openTailscale.ts` conserva su import diferido, también necesario para las pruebas puras de Node. Se comprueban la transformación, la llamada real al doble de Linking y las exportaciones de producción web y Android.

Actualización del 2026-10-04: al crecer v2, las tres pasadas calientes del gate serial superaron el presupuesto de 30 s. Con los mismos 672 casos y 46 suites, dos procesos de Jest dieron 13,695 / 13,634 / 13,590 s en componentes (mediana 13,634 s), sin omisiones ni fallos de aislamiento, manteniendo Android, DEMO=0 y React Compiler. Se limita la concurrencia a dos para aprovechar el equipo sin abrir un proceso por núcleo. La medición del gate completo y de su costo frío se registra por separado; este tiempo de componentes no acredita por sí solo esos presupuestos.

Actualización del 2026-10-05: con 824 casos y la suite de aceptación de V3, la mediana caliente del gate quedó unos 3 s sobre los 30 s, con `mobile:components` como camino crítico. A solas, el mismo Jest tarda 16,5 / 16,9 s con dos procesos, 9,8 / 10,1 s con cuatro, 7,9 / 8,2 s con seis y 7,5 / 7,1 s con ocho. Se sube el límite a cuatro: casi todo lo que da el paralelismo, sin abrir un proceso por núcleo en un equipo que comparten varias sesiones. Las mismas pruebas, sin omisiones; el gate da 24,45 / 27,87 / 34,23 s en caliente (mediana 27,87 s) y 35,53 s sin caché de Jest, con media de carga 32–53.

Actualización del 2026-10-06: Relay 3.1 empieza a usar reanimated y gesture-handler, que se tratan como límites nativos. No se escriben dobles propios: el arnés usa los que traen las bibliotecas. reanimated corre su implementación JS, cuyos fotogramas avanzan con el reloj simulado; para eso, un resolver de Jest (`tests/support/resolver.cjs`) envuelve el de la preset y salta los archivos `.native` de react-native-worklets, como indica worklets. gesture-handler carga su `jestSetup`, que entrega los eventos directamente a las retrollamadas de cada gesto. Las ayudas para leer el estilo animado y para arrastrar o mantener un gesto están en `tests/support/motion.ts` y `tests/support/gestures.ts`. Siguen React Compiler sobre el código propio, Android y `DEMO=0`; ninguna prueba depende de tiempos reales.
